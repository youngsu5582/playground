<details><summary>해설 — 내 답을 쓴 뒤에 펼친다</summary>

1. 표준 RR 은 팬텀을 허용하지만 PostgreSQL RR 은 **스냅샷 격리**라 트랜잭션 내내 같은 스냅샷을 본다 — 팬텀도 안 보인다(Q03 REPEATABLE READ 에서 팬텀).
   대신 스냅샷 격리는 **write skew 를 허용**한다(Q08 당직 둘이 동시에 빠지기). 같은 행을 동시에 고치면 나중 쪽이 40001 로 실패한다(Q07 스냅샷 이후 바뀐 행 고치기, first-updater-wins).
2. (a) 판단 근거가 되는 행들을 `SELECT … FOR UPDATE` 로 잠근다 — 두 번째 트랜잭션이 첫 번째 커밋을 기다린 뒤 판단한다.
   (b) **충돌을 구체화**한다 — 당직 인원 수를 담는 행 하나를 두고 둘 다 그 행을 갱신하게 만들면, 같은 행이라 행 락이 줄을 세운다.
   (c) 규칙을 DB 제약·트리거로 옮긴다. 셋 다 "서로 다른 행 → 같은 자원" 으로 바꾸는 것이 핵심.
3. 40001 은 "네가 읽은 세상은 이미 틀렸다"는 뜻이다. 앞에서 읽은 값에 근거한 판단 전체가 무효다.
   게다가 그 트랜잭션은 이미 실패 상태라 이후 문장은 전부 거절된다(25P02). 그래서 rollback 후 work 전체를 다시 실행한다.
   그 안에서 외부 API 호출·메시지 발행을 하면 재시도마다 중복된다 → 부수효과는 커밋 이후로 미루거나 outbox(02.03)로.
4. 옛 버전이 테이블에 남아 VACUUM 이 치워야 한다. 오래 열린 트랜잭션(특히 `idle in transaction`)은 "아직 누가 옛 버전을 볼 수 있다"며
   정리 기준선(xmin horizon)을 붙잡는다 → 테이블·인덱스 비대(bloat), 느려짐. `pg_stat_activity.xact_start` 감시,
   `idle_in_transaction_session_timeout` 설정이 실무 대응.
5. `UPDATE account SET balance = balance - :x WHERE id = :id AND balance >= :x` — 계산을 DB 안에서 하고 영향 행 수(0/1)로 성공을 판정한다.
   같은 행이라 행 락이 줄을 세우고, 기다린 쪽은 커밋된 최신 값으로 다시 평가한다(Q06 원자적 UPDATE 는 기다리나). 앱에서 읽고 계산해 쓰면 갱신 손실(Q05 읽고 계산해서 쓰기).
   비관 락(`FOR UPDATE`)·낙관 락(version) 과의 비교는 01.04.
