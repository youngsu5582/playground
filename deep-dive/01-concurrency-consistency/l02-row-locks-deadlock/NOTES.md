1. MVCC 라서 읽기는 락을 잡지도, 락에 막히지도 않는다. 공식 문서: "Row-level locks do not affect data querying; they block only writers and lockers to the same row." (Q02 락 걸린 행을 평범한 SELECT 로 읽기 — A 가 고치는 중인 행을 B 는 옛 버전 'pending' 으로 읽는다.)
   그래서 "읽고 → 판단하고 → 쓴다" 는 읽을 때 아무도 막지 않으니 위험하다. 판단 근거를 **읽는 순간 잠그려면** `SELECT … FOR UPDATE` 로 읽어야 한다 — 그러면 같은 행을 노린 쪽이 줄을 선다 (Q01 FOR UPDATE 로 잡힌 행을 UPDATE).
   단, 01.01 의 write skew 처럼 서로 다른 행이면 행 락이 겹치지 않는다.
2. NOWAIT: 못 잡으면 바로 55P03 (Q03 NOWAIT) — "지금 안 되면 안 하겠다" (예: 사용자 요청 중 즉시 응답). lock_timeout: 기다리되 상한을 둔다, 같은 55P03 (Q04 lock_timeout) — 안전망으로 세션에 거는 값.
   SKIP LOCKED: 잡힌 행을 없는 셈 치고 다음 행 (Q05) — 큐 소비자.
   NOWAIT · lock_timeout 이 실패하면 **트랜잭션이 중단 상태**가 되어 다음 문장은 25P02 (Q03). ROLLBACK 하고 처음부터. (PostgreSQL 에서 에러는 문장이 아니라 트랜잭션을 죽인다 — SAVEPOINT 로 문장 단위 복구는 가능하지만 앱이 명시해야 한다.)
3. `FOR UPDATE` 만 쓰면 두 번째 워커는 첫 워커의 커밋을 기다린다 (Q06 SKIP LOCKED 없이 LIMIT 1 FOR UPDATE). 깨어난 뒤 행이 조건에서 탈락하면 `LIMIT 1` 쿼리는 다음 행을 이어서 가져와 결과는 맞다 (실측: A 가 1번을 running 으로 바꿔 커밋하면, 깨어난 B 는 조건에서 탈락한 1번 대신 다음 pending 인 2번을 받는다 — Q06 의 B 가 받은 id 가 2).
   하지만 워커들이 한 줄로 선다 — 방법 검사가 잡는 것. SKIP LOCKED 의 대가는 문서가 경고한 "inconsistent view": 잡힌 행이 결과에서 조용히 빠지므로 "전체에 대한 일관된 답"이 필요한 쿼리(합계 등)에는 쓰면 안 된다. 큐처럼 "아무 하나면 된다"일 때만.
   처리 도중 워커가 죽으면 running 으로 남는다 — 재집기(lease 만료)는 별도 설계가 필요하다.
4. 서로의 행을 기다리는 원이 생기면, 기다림이 deadlock_timeout 을 넘긴 프로세스가 순환을 검사해 **자기 트랜잭션을** 40P01 로 abort 한다 (공식: "Exactly which transaction will be aborted is difficult to predict and should not be relied upon").
   이 랩에서 실측: A 가 먼저 기다리고 deadlock_timeout 이 지난 뒤에 B 가 순환을 닫으면 B 가 끊기고(Q10 반대 순서 데드락), A 가 기다린 직후(30ms 뒤) B 가 닫으면 A 가 끊긴다 — 먼저 타이머가 울린 쪽이 순환을 보기 때문이다. 즉 앱은 "누가 끊기나"를 가정하면 안 되고, 끊긴 쪽은 트랜잭션을 통째로 재시도해야 한다.
   예방: 모든 코드가 여러 행을 **같은 순서**로 잠근다 (구현 2: 작은 id 먼저 — 공식 문서의 권고). 순서를 정할 수 없으면(어떤 행이 필요한지 실행 중에야 안다) 40P01 재시도 + 짧은 트랜잭션 + 필요한 걸 한 번에 잠그기(`SELECT … WHERE id IN (…) ORDER BY id FOR UPDATE`).
5. 자식 INSERT 는 부모 행에 가장 약한 락(FOR KEY SHARE)을 건다. 부모의 이름 같은 키가 아닌 열을 UPDATE 하는 쪽(FOR NO KEY UPDATE)은 이것과 충돌하지 않아 기다리지 않는다 (Q08 자식 INSERT 가 부모 행에 거는 락). 키를 바꾸거나 DELETE 하는 쪽(FOR UPDATE)은 충돌해서 기다린다.
   표 13.3 으로는 자식 INSERT 끼리(KEY SHARE 끼리)도 서로 안 막는다. 이 충돌표는 공식 문서 표 13.3 이고, "자식 INSERT 가 FOR KEY SHARE 를 건다"는 부분은 이 랩에서 실측한 것이다.
