1. 유니크 제약은 "같은 키 행이 둘" 을 **끝까지 막는다**(Q01 확인하고 INSERT 교차 → Q02 유니크 제약의 두 번째 INSERT). 하지만 두 번째 시도는 에러(23505)로 돌아온다 — 호출자가 "이미 처리됨" 과 "진짜 오류" 를 구분해 기존 결과를 돌려주는 일은 여전히 앱 몫이다.
   게다가 에러를 받은 트랜잭션은 이후 문장이 전부 25P02 로 거절된다(Q09 23505 뒤의 다음 문장) — 같은 트랜잭션에서 기존 행을 SELECT 하려면 SAVEPOINT 가 필요하다(Q10 SAVEPOINT 로 감싸기). 제약은 심판이고, 심판 결과를 처리하는 흐름(재생 · 충돌 · 재시도)은 직접 짠다.
2. `DO NOTHING` 은 충돌 시 아무것도 안 하고 영향 행 수 0 · `RETURNING` 0행이다(Q06 DO NOTHING 의 영향 행 수) — "내가 선점했나" 를 영향 행 수 하나로 판정하기 좋다. 기다림은 그대로 있다(Q07 처리 중인 키에 DO NOTHING).
   `DO UPDATE … RETURNING` 은 충돌한 **기존 행**을 갱신하고 그 행을 돌려준다(Q08 DO UPDATE … RETURNING: payload 는 기존 값 first, hits 만 올라감) — 한 문장으로 기존 결과까지 읽어 올 수 있지만, 충돌할 때마다 행을 써서 락·WAL·dead tuple 이 생긴다. 선점 판정엔 DO NOTHING, "카운터 올리며 현재 값 읽기" 엔 DO UPDATE.
3. JVM 락은 그 JVM 안만 안다. 서버가 2대면 각자 "처음 보는 키" 라 둘 다 처리한다 — 방법 검사 테스트가 이걸 거른다. 심판은 모든 서버가 공유하는 곳(DB)에 있어야 한다.
   `payments` 에 키 컬럼 + 유니크 제약을 걸면 중복 **행**은 막히지만, 그 전에 이미 외부 결제 API 가 호출됐다 — 돈은 나갔고 DB 에러만 난다. 외부 부수효과보다 **앞에서** 선점해야 한다.
   그래서 키 선점이 1차 방어이고, `payments.idempotency_key UNIQUE` 는 선점 로직이 틀렸을 때의 2차 안전망으로 **같이 둔다**. (이 레슨은 빈칸 버그가 가려지지 않게 일부러 뺐다 — 있으면 빈칸 상태에서도 중복 행이 막혀 결과 검사가 덜 빨개진다.)
4. 지문은 "비즈니스적으로 같은 요청" 을 정하는 결정이다. 전부 해시하면 필드 순서·타임스탬프 때문에 항상 충돌하고, 너무 적게 보면 다른 요청을 같다고 본다. 이 레슨은 고객 + 금액이다.
   실패 저장은 갈린다. 이 레슨은 실패하면 롤백으로 키가 사라져 재시도할 수 있다("재시도로 결과가 달라질 수 있나?" 가 기준). 반면 Stripe 는 첫 요청의 결과를 실패·500 까지 저장해 같은 키엔 같은 결과를 준다 — 대신 클라이언트는 새 키로 다시 시도한다. 둘 다 유효한 설계이고, 계약으로 문서화해야 한다.
5. 먼저 커밋하면 커넥션을 오래 안 쥔다. 대신 IN_PROGRESS 가 **커밋된 채** 남으므로, 같은 키가 또 오면 "기다릴까 · 409 로 돌려보낼까" 를 정해야 하고, 서버가 죽으면 영영 IN_PROGRESS — 그래서 lease(만료 시각)가 필요하다. 한 트랜잭션 설계는 죽으면 롤백으로 키가 같이 사라져 lease 가 필요 없는 대신, 외부 호출 내내 커넥션을 쥔다.
   이 레슨 설계에서 "처리 중인 같은 키를 기다린다" 는 곧 **DB 락 대기**이고, 기본값(`lock_timeout = 0`)은 무제한이다. 실무에선 `SET lock_timeout` 을 걸어 시간 안에 못 풀리면 409 (처리 중, 잠시 후 재시도) 로 돌려보낸다 — 타임아웃 에러(55P03)는 선점 실패와 같은 "아직 모른다" 로 다룬다.
   어느 쪽이든 "외부 결제는 성공했는데 커밋 직전에 죽었다" 틈은 남는다 — 외부 쪽에도 멱등 키를 전달하거나(결제사 API), outbox(02.03)로 푼다.
