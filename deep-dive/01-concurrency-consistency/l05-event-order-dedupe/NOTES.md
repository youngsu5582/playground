1. 상태를 "값으로 덮는" 부분만 보면 같은 이벤트를 두 번 해도 결과가 같다(멱등). 하지만 반영에 **부수 효과**(알림 · 포인트 적립 · 카운터 증가)가 붙으면 두 번 일어난다 — `change_count` 가 2 (Q01 같은 이벤트 두 번).
   또 "덮어쓰기" 는 순서에 약하다: 같은 이벤트의 재전달이 **다른 이벤트 뒤에** 오면 되돌아간다. 중복과 역전은 따로 막는다.
2. messageId 만 있으면 v3 다음에 *처음 보는* v2 메시지가 오면 통과해서 상태가 되돌아간다 (Q02 늦게 온 과거 이벤트) — 다른 메시지의 역전은 messageId 로 못 거른다.
   version 만 있으면 상태는 지켜지지만(Q03 조건부 UPDATE), 같은 메시지가 재전달됐는지 알 수 없다. 그래서 "STALE 로 무시한 메시지" 와 "처음 오는 메시지" 를 구분하지 못하고,
   version 을 상태 갱신 밖의 부수 효과(알림 발송 등)에 쓸 수 없다. 요약: messageId = 재전달(같은 메시지) 거르기, version = 역전(다른 메시지) 거르기.
3. 먼저 커밋된 inbox 는 "처리했다" 고 말한다. 그 뒤 반영이 실패하면 재전달은 inbox 가 이미 있어 DUPLICATE 로 건너뛴다 → 상태는 READY 로 남는다 (Q05 inbox 먼저 커밋 후 반영 실패).
   한 트랜잭션이면 반영 실패와 함께 inbox 도 롤백돼 재전달이 정상 반영된다 (Q06 한 트랜잭션) — **재전달이 곧 재시도**다.
4. inbox 의 PRIMARY KEY(유니크 인덱스)가 같은 키의 두 번째 INSERT 를 첫째 트랜잭션의 끝까지 기다리게 한다 — 이 대기는 Q09(같은 messageId 동시 · 먼저 온 쪽이 롤백)에서 실측(엔진의 `pg_stat_activity` 로 Lock 대기 확인)했고, 공식 문서는 INSERT 페이지의 ON CONFLICT 절("원자적 INSERT 또는 UPDATE 결과 보장")과 13.2 Read Committed 절을 본다. 첫째가 커밋하면 둘째는 0행(DUPLICATE), 첫째가 롤백하면 둘째가 1행을 넣고 계속 진행한다 (Q09).
   그래서 inbox INSERT 가 반영과 같은 트랜잭션 안에 있어야 한다.
5. 순서 키가 없으면: 외부 시각(`occurredAt`)은 시계 오차 때문에 위험하다 — 전이표(허용된 후퇴만 허용) 또는 외부 시스템 조회(최신 상태 폴링 · 대사)로 보정한다. 상태 enum 의 rank 도 쓸 수 있지만 정당한 후퇴(반송)를 놓친다.
   inbox 는 무한히 커지므로 보관 기간을 정하고 지운다. 기간은 브로커가 재전달할 수 있는 최대 지연보다 길어야 한다 — 짧으면 오래된 중복이 뚫린다. 그래서 반영 자체를 멱등(`WHERE version < v`)으로 두는 게 최종 방어다. (보관 기간 · 외부 키 설계는 이 레슨에서 실측하지 않은 일반 지침)
