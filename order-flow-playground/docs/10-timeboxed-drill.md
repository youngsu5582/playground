# 10 — 60분 드릴 운영법

> 60분 안에 평가되는 건 **완성된 코드가 아니라 진행 방식**이다.
> 완벽한 코드를 시간 초과로 못 끝내는 것보다, 단순한 코드를 끝내고 한계를 설명하는 쪽이 낫다.

---

## 1. 타임박스

| 구간 | 시간 | 하는 일 | 실패 신호 |
|---|---|---|---|
| ① 재진술 | 0–5분 | 요구사항을 내 말로 되풀이 | 바로 타이핑 시작 |
| ② 질문 | 5–10분 | 애매한 조건 3~5개 확인 | 질문 없이 가정만 함 |
| ③ 뼈대 | 10–20분 | 타입·시그니처·정상 경로 | 처음부터 추상화 |
| ④ 테스트 | 20–35분 | 정상 → 경계 → 예외 | 끝까지 짜고 나중에 테스트 |
| ⑤ 보완 | 35–50분 | 중복·동시성·예외 처리 | 여기부터 시작 |
| ⑥ 정리 | 50–60분 | 복잡도 + 실서비스 확장 설명 | 시간 다 쓰고 침묵 |

**①②를 건너뛰면 ⑤에서 반드시 되돌아온다.** 10분 투자해서 30분을 아끼는 구간이다.

---

## 2. 구간별 스크립트

말이 막힐 때 그대로 꺼내 쓸 문장들.

### ① 재진술 (0–5분)

> "제가 이해한 요구사항은 ○○를 받아 ○○를 판정하고, ○○인 경우는 무시하는 겁니다. 맞을까요?"

### ② 질문 (5–10분) — 이 다섯 축에서 고른다

| 축 | 질문 예시 |
|---|---|
| **중복** | "같은 요청이 두 번 들어올 수 있나요? 판단 기준은 무엇인가요?" |
| **순서** | "입력 순서가 보장되나요? 늦게 도착한 과거 데이터가 있을 수 있나요?" |
| **동시성** | "동시 호출을 고려해야 하나요, 단일 스레드로 가정할까요?" |
| **실패** | "중간에 실패하면 전체 롤백인가요, 부분 성공을 허용하나요?" |
| **경계** | "빈 입력 / 음수 / null 은 어떻게 처리할까요?" |

> 💡 다섯 개를 다 묻지 않는다. **문제에 맞는 2~3개**를 골라 묻는 게 더 좋게 읽힌다.
> 무의미한 질문을 채우는 건 시간을 태우는 것과 같다.

### ③ 뼈대 (10–20분)

> "일단 정상 경로만 단순하게 만들고, 동시성은 그다음에 붙이겠습니다."

- 타입 먼저 (enum, record). 도메인 어휘가 코드에 드러나게
- 상태 저장은 `Map` 으로 시작. **DB·프레임워크 얘기는 나중에 말로**
- 추상 인터페이스, 전략 패턴, 제네릭 — **전부 나중에**. 지금 넣으면 시간만 먹고 평가에 도움 안 된다

### ④ 테스트 (20–35분)

네 묶음 순서로 짠다:

```
정상  → 거부  → 종료/경계  → 동시성
```

> "먼저 규칙을 테스트로 못 박고 구현하겠습니다."

### ⑤ 보완 (35–50분)

여기서 처음으로 중복·동시성·예외를 넣는다. 순서를 지키는 게 중요하다 — 단일 스레드가 초록이 된 다음에 스레드를 붙여야 실패 원인이 하나로 좁혀진다.

### ⑥ 정리 (50–60분) — **이 문장이 점수를 만든다**

> "현재 구현은 단일 프로세스 메모리 기반의 단순화 버전입니다.
> 실서비스라면 상태와 처리 이력을 DB에 두고 unique 제약으로 중복을 막겠습니다.
> 인스턴스가 여러 대면 메모리 자료구조로는 부족하기 때문입니다.
> 그리고 실패한 건을 나중에 찾아 재처리할 수 있도록 원본과 실패 사유를 남기겠습니다."

시간이 부족해 못 짠 부분이 있으면 **숨기지 말고 말한다**:

> "동시성 처리는 시간상 못 넣었는데, `ConcurrentHashMap.compute` 로 키 단위 원자 갱신을 하거나 DB 조건부 UPDATE 로 처리하면 됩니다."

## 3. 흔한 실패 5가지

| # | 실패 | 처방 |
|---|---|---|
| 1 | 질문 없이 바로 코딩 | ②를 의식적으로 5분 확보 |
| 2 | 처음부터 인터페이스·제네릭 | 구체 클래스로 시작. 리팩터링은 시간이 남으면 |
| 3 | 테스트를 마지막에 | 정상 케이스 1개는 구현 직후에 |
| 4 | 침묵 | 막히면 **막혔다고 말한다**. "지금 A와 B 중 고민 중인데 A로 가겠습니다" |
| 5 | 시간 초과 후 미완성 | 50분에 무조건 손 떼고 정리 시작 |

**4번이 가장 크다.** 화면에 코드가 안 늘어나는 5분 동안 아무 말이 없으면, 상대는 무슨 생각을 하는지 알 수 없다. 생각을 소리 내는 것 자체가 평가 대상이다.

---

## 4. 도구를 써도 되는 경우

검색·AI 사용이 허용되는 자리라면, 쓰는 것 자체는 감점이 아니다. **검증 없이 붙여넣는 것**이 감점이다.

권장 흐름:
```
문제 이해 → 설계 결정(내가) → 생성(도구) → 읽고 검증(내가) → 테스트로 확인 → 설명
```

- 생성된 코드에 **테스트를 내가 추가**한다 — 이게 검증했다는 증거
- 왜 이 코드가 맞는지 설명할 수 없으면 **버리고 직접 쓴다**
- 도구가 만든 것과 내 결정을 구분해서 말한다: "이 부분은 생성해서 검증했고, 정렬 기준은 제가 정했습니다"

> ⚠️ 가장 나쁜 시나리오: 생성된 코드가 돌아가는데 왜 돌아가는지 설명 못 하는 상황. 코드가 완성될수록 감점이 커진다.

## 5. 드릴 실행

```bash
# 스테이지 하나 red 상태 확인
cd app && ./gradlew s1

# 60분 타이머와 함께 시작
../scripts/01-drill.sh 1

# 진행 상황(구현률) 확인
../scripts/02-progress.sh
```

### 반복 권장 순서

| 회차 | 스테이지 | 노리는 것 |
|---|---|---|
| 1 | stage1 | 전이표·테스트 4묶음 구조 몸에 익히기 |
| 2 | stage2 | 멱등성 + 첫 동시성 |
| 3 | stage3 | 동시성 본격 — **깨지는 걸 보고 고치기** |
| 4 | stage4 | 이벤트 3중 방어 |
| 5 | stage5 | Comparator + 자료구조 선택 설명 |
| 6+ | 무작위 1개 | **아무 준비 없이 60분** — 실전 시뮬레이션 |

6회차부터가 진짜 연습이다. 이미 답을 아는 문제를 다시 푸는 건 워밍업일 뿐이다.

## 6. 끝나고 남길 것

매 회차 후 `TESTING.md` 의 기록 템플릿에 3줄만 남긴다.

```
D-01 / stage3 / 2026-08-13
막힌 곳: 동시성 테스트가 간헐적으로만 실패해서 원인 파악에 15분 소모
배운 것: 경쟁 상태는 repeat 로 반복 실행해야 재현된다. 1회 초록은 증명이 아니다
다음 개선: 단일 스레드 초록 → 동시성 순서를 지킬 것 (섞어서 하다 시간 태움)
```

**"막힌 곳" 을 남기는 게 핵심**이다. 같은 곳에서 두 번 막히면 그게 진짜 약점이다.
