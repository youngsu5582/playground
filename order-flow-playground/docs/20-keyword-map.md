# 20 — 키워드 지도와 경험 번역

> 새 능력을 만드는 게 아니다. **이미 한 것을 상대가 쓰는 어휘로 옮기는 작업**이다.

---

## 1. 다섯 스테이지가 실제로 가리키는 것

| 스테이지 | 표면 주제 | 실제로 증명하는 능력 |
|---|---|---|
| 01 상태 전이 | enum + Map | 규칙을 데이터로 표현 / 변경에 강한 설계 |
| 02 멱등성 | 중복 요청 | 분산 환경의 재시도 / at-least-once 대응 |
| 03 동시성 | 재고 차감 | 경쟁 상태 / 락 범위 / 트랜잭션 |
| 04 이벤트 순서 | 상태 통지 | 비동기 소비 / 관측성 / 재처리 |
| 05 우선순위 | 정렬 | 자료구조 선택 근거 / 복잡도 / 운영 지표 |

**하나의 축**으로 묶으면: *외부 시스템과 내부 상태를 어긋나지 않게 유지하는 일.*

이 축은 도메인과 무관하다. 결제든 주문이든 예약이든 좌석이든 크레딧이든, 다루는 문제는 같다.

---

## 2. 키워드 지도

이력서·대화에서 실제로 신호가 되는 단어들. **단어만 아는 게 아니라 "언제 이걸 쓰고 언제 안 쓰는지" 를 말할 수 있어야** 의미가 있다.

### 상태 · 정합성
```
상태 전이 · 상태 머신 · 종료 상태 · 상태 이력 · append-only
불변식(invariant) · 정합성 · 대사(reconciliation) · 보정 배치
```

### 중복 · 재시도
```
멱등성(idempotency) · 멱등키 · unique 제약 · at-least-once · exactly-once(는 환상)
재시도 · 지수 백오프 · jitter · 재시도 가능/불가능 실패 구분
```

### 동시성 · 트랜잭션
```
경쟁 상태 · check-then-act · 원자적 연산 · 조건부 UPDATE
비관적 락 · 낙관적 락 · 버전 컬럼 · SELECT FOR UPDATE · SKIP LOCKED
락 범위 · 락 순서 · 데드락 · 트랜잭션 경계 · 격리 수준
```

### 비동기 · 메시징
```
프로듀서/컨슈머 · 파티션 키 · 순서 보장 범위 · 컨슈머 그룹
중복 소비 · 순서 역전 · DLQ · 재처리 · outbox 패턴 · 이벤트 이력
```

### 운영 · 관측성
```
구조화 로그 · correlation ID · 성공/실패 카운터 · 처리 지연(latency)
backlog · 최고령 대기 시간 · p99 · 알람 임계값 · stuck 감지 · 런북
```

### 품질
```
테스트 4묶음(정상/거부/경계/동시성) · 동시성 반복 검증 · 결정론적 순서
외부 API mock · 통합 테스트 · 코드 리뷰 · CI
```

> ⚠️ **함정**: 키워드를 나열하면 오히려 얕아 보인다. **한 문장에 하나씩, 사건과 함께** 등장해야 한다.
> "Kafka, Redis, 멱등성, DLQ 경험" ← 이건 신호가 아니라 소음이다.

## 3. 경험 번역 — 3단 문장

이미 한 일을 이 틀에 넣으면 도메인을 모르는 사람도 이해한다.

```
[어떤 실패가 전제된 상황에서]  [무엇을 보장했고]  [어떻게 확인했는가]
```

세 번째 칸이 비면 주장이 되고, 채우면 근거가 된다. **"확인했다" 가 들어가는지가 갈림길**이다.

### 번역 예시

| 약한 표현 | 강한 표현 |
|---|---|
| 결제 API 를 개발했습니다 | 외부 결과 통지와 내부 반영을 분리하고, 중복 통지·순서 역전에 대비해 멱등 처리와 사용자 단위 락을 적용했습니다. 동시 요청 테스트로 이중 반영이 없음을 확인했습니다 |
| Kafka 를 사용했습니다 | at-least-once 전제 위에서 컨슈머를 멱등하게 만들고, 재시도 불가 실패는 DLQ 로 보내 원본과 사유를 남겨 재처리할 수 있게 했습니다 |
| 배치를 만들었습니다 | 대량 삭제를 저부하 시간대에 청크 단위로 돌리고, 실패 건의 상태를 남겨 다음 회차가 이어받도록 했습니다 |
| 비동기 처리를 했습니다 | 단계별 상태를 기록해 중간 실패 시 처음이 아니라 **실패한 단계부터** 재개하도록 만들었습니다 |

### 도메인 어휘 대응표

한 도메인에서 겪은 문제는 다른 도메인에 그대로 있다. **어휘만 갈아끼우면 된다.**

| 이 플레이그라운드 | 결제·크레딧 | 예약·티켓 | 비동기 작업 파이프라인 |
|---|---|---|---|
| 주문 상태 | 결제/충전 상태 | 예약 상태 | 작업 상태 |
| 재고 예약 | 잔액 홀드 | 좌석 선점 | 슬롯/쿼터 확보 |
| 예약 만료 | 홀드 해제 | 선점 시간 초과 | 타임아웃 |
| 배송 이벤트 | 결제 결과 통지 | 공급자 상태 통지 | 외부 API 콜백 |
| 중복 이벤트 | 통지 재전송 | 중복 예약 요청 | 메시지 재소비 |
| 출고 확정 | 실제 차감 | 발권 | 결과 확정 |

> 💡 이 표를 읽는 방향이 중요하다. **"물류를 몰라서 불리하다" 가 아니라 "같은 문제를 다른 이름으로 이미 다뤘다"** 로 정리된다.

## 4. 예상 질문과 답의 뼈대

각 항목은 **결론 → 이유 → 확인 방법** 순으로 답한다.

### 상태·정합성
- 상태를 어디에 저장했고, 이력은 어떻게 남겼나
- 현재 상태와 이력을 나눈 이유는
- 상태가 어긋난 걸 어떻게 발견하나 (← **대사·알람**이 답에 나와야 한다)

### 중복·멱등
- 중복 요청이 들어오면 어떻게 되나
- 멱등키는 누가 만드나 (← 클라이언트)
- 멱등 레코드는 언제 지우나
- 실패한 요청도 멱등 처리 대상인가 (← 실패 유형별로 다르다)

### 동시성
- 동시에 같은 자원을 건드리면
- 왜 그 락을 골랐나 / 락 범위는
- 트랜잭션 경계는 어디까지인가
- 그 안에서 외부 API 를 호출하나 (← **하면 안 된다**. 이유를 말할 수 있어야)

### 비동기·실패
- 왜 동기가 아니라 비동기인가
- 메시지가 중복 소비되면
- 순서가 뒤바뀌면
- 재시도해도 계속 실패하면
- 실패한 건을 나중에 어떻게 찾나 (← 상태 + 실패 사유가 남아 있어야 찾는다)

### 운영
- 문제가 생긴 걸 어떻게 아나
- 무엇을 로그로, 무엇을 지표로 남기나
- 장애 시 복구 순서는
- 테스트하지 못한 영역은 무엇인가 (← **정직하게 답하는 편이 낫다**)

## 5. 마지막 질문에 대한 답

> "이 일을 하면 다음에 어디로 갈 수 있나?"

이 다섯 스테이지가 다루는 문제(상태·정합성·중복·동시성·비동기·재처리)는 특정 산업의 것이 아니다.
**돈·재고·좌석·작업처럼 "틀리면 실제 손해가 나는 상태"를 다루는 모든 시스템**에 있다.

커머스·주문·정산·결제·예약·물류·SCM·배차 — 이름은 다르지만 채용 공고에서 찾는 신호는 같다:

```
주문 · 재고 · 정산 · 상태 · 정합성 · 멱등 · 동시성
event · reconciliation · idempotency · allocation · reservation
```

**도메인 이름이 아니라 이 단어들로 검색하는 것**이 커리어 축을 넓히는 방법이다.
